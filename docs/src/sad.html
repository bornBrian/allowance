        Introduction

        Purpose

        This document describes the architecture of Allowance 1.0: how the system is divided, how its parts work together, where it runs, and why it is built this way. It shows how the requirements in ALW-SRS are met, and records the decisions and their alternatives so that later changes can be judged against the reasons behind them.

        Scope

        The description covers the whole system: the web page, the server, its data, and its use of PayPal, Channel3, the Claude API and Cloudflare Turnstile. The internal design of those external services is outside its scope.

        Layers

The decision logic sits at the bottom with no dependencies, so it can be tested without a network or a database. The rule was checked against the source on 4 November 2026: no module imports from a layer above its own.

        The guard

        The guard is the centre of the design. Its signature is decide(proposal, checkout, rules, history, now, requestMax) → { verdict, amount, checks, reasons }. It reads no clock, network, database or environment: everything it uses is passed in. The same inputs always give the same output, which is what makes every rule in ALW-SRS section 3.3 testable in isolation. It runs the ten checks of ALW-SRS table 11 in order, adds a check with a sentence for each, and combines them by BR-04.

        Changing a rule means changing this one file and its tests. No other component computes limits, budgets or amounts.

        Linking PayPal

        The setup token is remembered against the wallet that created it, so a token approved in one browser cannot be attached to another wallet (ACC-02).

        The category and any requested price are fixed in step 3, from the request alone, before the agent reads any product data. The agent can only buy a product it found itself (step 11), and only once. The decision in step 14 is made by the guard, not by the model.

        Consistency

        Each change is a single SQL statement, so it is atomic without explicit transactions. Status changes are written as UPDATE … SET status = to WHERE id = ? AND status = from and succeed only if the row was still in the expected status. Counters use INSERT … ON CONFLICT DO UPDATE … RETURNING count, so two requests cannot both read the old count.

        Concurrency view

        The server is one Node.js process. Requests are handled concurrently on its event loop; SQLite serialises writes, with a 5 s busy timeout. lists every place where two things could happen at once and how each is resolved.

        Concurrency hazards and controls.

        HazardControlRequirement
        Two agent runs for one wallet (two tabs)In-process set of wallets with a run in progress; the second gets 409AC-02
        Claude calls buy twice in one turnA flag set before any await; the second call is refusedREQ-04
        Approve tapped twice, or approve and decline togetherConditional status update; only one succeedsAPR-03
        Refund tapped twiceConditional update from paid to refundedRLB-02
        A charge request retried after a timeoutPayPal request id equal to the purchase idPAY-03
        Two requests increment the same counterSingle upsert statement with RETURNINGAC-01

        The run lock is held in memory, which is correct only for a single instance. Running several instances would require moving it into the database. This is recorded as a constraint (CON-05) and a risk (section 14).

        Cross-cutting concepts

        Errors

        Two error types carry messages written for people: UserError with an HTTP status, and its subtype LimitReached, which adds a Retry-After value. Every route maps errors in one place: these types become their message and status; anything else is logged on the server and replaced by a general message with status 500.

        Input cleaning

        All text from people and shops passes through one module: Unicode NFKC normalisation, removal of zero-width and direction-override characters, replacement of control characters, whitespace folding and a length cap. Links are accepted only as https without embedded credentials. Shop domains are lower-cased and stripped of anything that cannot appear in a domain.

        Rate limits and quotas

        Limits are fixed windows counted in the database. The key is action : wallet-or-ip : id : window-length : window-start; the count is incremented in one statement and compared with the limit. When exceeded, the wait is the time to the end of the window. Each action has limits per wallet and per IP (ALW-SRS table 14). Fixed windows can allow up to twice the limit across a window boundary; this is accepted.

        Cost accounting

        After every Claude call, its cost is computed from the reported token usage at Claude Opus 5.5 prices and added to the day's total: cost = (input × 4 + output × 20 + cache write × 5 + cache read × 0.2) ÷ 1,000,000 US dollars. Before every call, the day's total is compared with DAILY_AI_BUDGET_USD. Channel3 calls are counted per calendar month against CHANNEL3_MONTHLY_LIMIT.

        Request identifiers sent to PayPal.

        CallPayPal-Request-IdEffect of a repeat
        Create setup tokenNew random idNew token; harmless

        Money and time

        Amounts are whole cents from the moment they enter the system; dollars from rules are rounded to the nearest cent. PayPal receives two-decimal strings. Periods are computed in UTC: weeks from Monday, months from the 1st.

        Configuration and secrets

        All configuration is read from environment variables (appendix B). Secrets are never written to the repository, logs or the browser; the only value the browser receives is the public PayPal client id and, if configured, the public Turnstile site key.
